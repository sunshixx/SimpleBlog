# 2026-08-21

## 博客 v2.0：JSON 存储 → Markdown 文件存储 + 图片库

### 改造背景
原 `db/articles.json` 单文件存全部文章（已膨胀到 33KB），用户希望改用更轻量的数据库方案。

### 方案
**采用每篇文章一个 .md 文件 + YAML frontmatter**（零依赖、最轻量）：
- `db/articles/{id}.md` 每篇一个文件，frontmatter 存元数据（id/title/category/author/date/time/weekday/subscription/comments/tags/summary），正文为 Markdown
- 启动时全量扫 `db/articles/` 目录构建内存索引，CRUD 同步到对应 .md 文件
- 优点：备份/git diff 看得见、JSON 永不膨胀、单篇损坏不连累其他

## v2.1：去 AI 味 UI + 粘贴板支持 + 上传任意路径 + 发布时归档

### 用户反馈
1. admin 编辑器图片库 UI 太花哨（彩色按钮、modal 弹窗、grid 卡片）—— AI 味重，跳脱原生 LWN.net 审美

3. 上传图片不应固定 picture 路径；上传可以是任意路径，发布时再统一拷贝到 picture/ 归档

### 改造方案

**UI 改造（去 AI 味）**：
- 删除 modal-mask/modal-box/pic-card/pic-grid/editor-toolbar/tb-btn 等所有花哨 CSS
- 改成 LWN 原生审美：朴素的 `<details class="pic-section">` 折叠区，里面是 form 风格的 input + 按钮（用 var(--ButtonColor) 桃色按钮，var(--FormBG) 灰底）

**粘贴板支持**：
- textarea 监听 paste 事件
- 检测 clipboardData.items 中的 image/*
- 自动上传到 picture/（粘贴路径无机会选路径，直接归 picture）
- 上传成功后在光标处插入 `![name](picture/xxx.png)`
- 用文件名 `paste-<timestamp>.<ext>`

**上传任意路径**：
- 上传表单加路径输入框（默认 "picture"）
- POST /api/pictures 接受 multipart 表单字段 `path`，保存到 ROOT 内任意相对目录
- `safeRelativeDir()` 防目录穿越（拒绝 ../、绝对路径）
- 返回 `ref` 字段是相对于 ROOT 的 markdown 引用路径（如 `images/foo.png`）

**发布时归档（核心新功能）**：
- `archivePicturesInContent(content)` 扫描 markdown 中所有本地图片引用
- 跳过 `picture/` 开头（已归档）、外链（http/https/data:）、绝对路径（/开头）
- 其他的本地相对路径：调用 `archivePictureRef(relPath)` 物理拷贝源文件到 picture/ 下，返回新引用
- 重写 markdown 中的引用为 `picture/<filename>`
- 同名自动加序号（`foo.png` → `foo_1.png`）
- 源文件保留（拷贝而非移动）
- 在 `createArticle` 和 `updateArticle` 中都调用

### API 变化
- `GET /api/pictures?dir=xxx` 可列出任意 ROOT 内目录的图片
- `POST /api/pictures` 接受 multipart 字段 `path`，指定保存目录
- 响应新增 `ref` 字段（markdown 引用路径）

### Bug 修复
- `handleAPI(req, res, pathname, method)` 缺少 `urlObj` 参数 → 改为 `handleAPI(req, res, pathname, method, urlObj)`
- `deletePicture` / `deleteArticleFile` 在 sandbox trash hook 报错时，以"文件最终不存在"为准判断成功

## v2.3.1：路径检查 Windows 兼容性 bug 修复

### 问题
v2.3 中把 `serveStatic` 改成 `path.resolve(ROOT, pathname)`，但在 Windows 上 `path.resolve(ROOT, '/index.html')` 把 `/index.html` 当作绝对路径，**绕过 ROOT**，结果 `C:\index.html`，导致所有页面都 403。

### 修复
- 改用 `path.resolve(path.join(ROOT, pathname))`：
  - `path.join(ROOT, '/index.html')` = `C:\Users\DP\...\blog\index.html`（join 把前导 / 当片段）
  - `path.resolve` 拿到标准绝对路径
  - startsWith(ROOT+sep) 严格检查防 ../ 逃出

### 教训
- **Windows 路径陷阱**：`path.resolve(ROOT, '/abs/path')` 不会用 ROOT 作为基准，会把 `/abs/path` 当作绝对路径。必须用 `path.join` 先拼起来。
- 这类 bug 在 Linux/Mac 上不会复现（POSIX 路径语义不同），所以本地开发可能测不出来，要在 Windows 上验。

### 验证结果
- 全部正常页面（/ /index.html /admin.html /article.html /tags.html /search.html /about.html /css/* /js/* /picture/*） → 200 ✓
- 路径穿越（/..%2Fconfig.json /picture/..%2F..%2Fconfig.json 等） → 403 ✓

## v2.5：浏览器后退刷新 v2 + 首页 LWN archive 改版

### 1. bfcache 修复 v2（覆盖非 bfcache 后退场景）
v2.4 用 `if (e.persisted) init()`，但很多场景不走 bfcache（iOS Safari、提交评论破坏缓存等），persisted=false 时代码不做任何事。

**改动**：
- 引入 `_initialRenderDone` 标志，首次渲染完成才置 true
- pageshow 不再判断 e.persisted，只要 `_initialRenderDone === true` 就用 requestAnimationFrame 异步重跑 init
- 所有 GET（fetchArticles / fetchArticle / fetchTagIndex / fetchComments）加 `cache: 'no-store'`，避免 HTTP 缓存命中带回来旧评论数
- 这样覆盖：bfcache 恢复（persisted=true）、普通后退重载、移动端 Safari、back_forward navigation type

### 2. 首页 LWN archive 改版
用户截图反馈：现有"精选文章+简讯折叠"用 HeadlineBG 桃色背景单独卡片太丑，要 LWN archives 那种简洁风：每"期"一个带下划线标题，下面按 Front/Kernel/Security/.../Briefs/Announcements 桶列出 bullet 链接。

**改动**：
- 删掉原本的居中搜索框 + 精选文章块 + 简讯折叠按钮
- 改成 ISO 周分组：`getISOWeek(dateStr)` 算年+周号，组 key = `2026-W34` 形式

- 渲染：`<h3 class="SummaryHL">OSS Notes Weekly Edition for August 20, 2026</h3>` + `<ul class="NoBullet spacylist">` 列出各桶

## v2.7：全面 bug 修复（含 1 个 P0 安全漏洞）

### 用户反馈 v3
"你先跑一下测试看看还有什么bug或者逻辑错误嘛。全部页面逻辑跑一下"

### 测试方法
1. 静态 review：node --check 6 个 JS 文件 + grep 风险模式 + 人工 review
2. API 端到端：bash 脚本跑 19 个 API 测试用例（GET / POST / PUT / DELETE / CORS / 防重复 / 路径穿越 / 401 / 404）
3. 前端纯函数：Node + vm sandbox 注入 mock window/document，跑 21 个测试用例（escapeHtml XSS / highlightMatch / formatDate / formatCommentBody / ISO 周 / homeArticleBullet 各字段）
4. 安全边界：长 author / 长 content / 路径穿越 / 静态白名单

### 发现并修复的 bug

**P0 — server 静态文件白名单缺失（严重）**
- `server.js` 的 `serveStatic` 只检查 `filePath.startsWith(ROOT+sep)`，没限制 pathname 范围，导致：
  - `GET /db/config.json` → 200 直接返回 `{"password":"admin123"}`
  - `GET /server.js` / `/migrate.js` / `/seed.js` → 后端源码可下载
  - `GET /.git/HEAD` → git 元数据可下载
  - `GET /db/articles/1.md` / `/db/comments/1.json` → 全部数据可下载
- **修复**：新增 `STATIC_WHITELIST_HTML`（/ /index.html /about.html /article.html /search.html /tags.html /admin.html）+ `STATIC_WHITELIST_PREFIX`（/css/ /js/ /picture/）两套白名单；不在白名单内的 pathname 直接 404。原有 startsWith(ROOT+sep) 二次防穿越保留。

**P1 — renderMathIn 无限重试**
- KaTeX CDN 加载失败时 `setTimeout(tryRender, 50)` 永远不会停，CPU 浪费
- 同时如果 el 是 null（document.querySelector 没找到），`renderMathInElement(null, ...)` 会抛 TypeError 被吞，但 setTimeout 已经在跑
- **修复**：加 60 次重试上限（约 3 秒）+ el null 时直接 return

**P2 — addComment 浪费 ID**
- `CURRENT_COMMENT_ID++` 在校验空内容之前执行
- 用户提交空内容评论 → 400，但 ID 已经被吃掉，下次正常评论 ID 跳一格
- **修复**：先校验 content 非空，再 `CURRENT_COMMENT_ID++`

**P3 — 死代码 js/data.js 仍被 5 个 HTML 引用**
- 20KB 旧静态数据（含全部文章正文）每次首屏加载，但 app.js 实际走 API
- **修复**：从 index/article/search/tags/about.html 去掉 `<script src="js/data.js">`（保留文件本身，admin.js 也没引，向后兼容）

### 测试结果
- node --check 6 个 JS 文件全部 OK
- API 19 项全 PASS（含修复后再次跑一次完整 create + delete 循环）
- 前端 21 项纯函数全 PASS
- 静态白名单 24 项全 PASS（11 个敏感路径 404 + 12 个允许路径 200 + 1 个路径穿越 403）

### 教训
- **静态文件服务必加白名单**：startsWith(ROOT+sep) 只是防穿越，不限制路径范围。任何 ROOT 内的文件（包括源码、配置、git）都能被下载。dev 环境的"图方便"在生产环境是 P0 漏洞。
- **资源加载失败的兜底必须有上限**：retry loop 不加上限就是定时炸弹，CDN 挂掉 / 网络异常 / 防火墙拦截任意一个都会触发。
- **测试要从用户视角全栈跑**：curl 只测 API 是不够的；要测静态文件返回什么（白名单）+ 前端纯函数（XSS / 数据格式 / 排序）+ 端到端流程（create → comment → delete → 验证清理）。

- **管理员 token 与普通用户 token 隔离**：普通用户 token 不能创建/编辑/删除文章（管理员 token 才能）。这样保持原有 admin CRUD 工作流不破坏，又给了普通用户"登录"的体验

- **token 存内存是 dev 妥协**：重启 server 后所有 token 失效，用户需重新登录。生产应该用 Redis 或签名 JWT

### 测试（18 项全 PASS）
- 注册/重复注册/短密码/无效用户名 校验
- 登录正确/错误密码
- /api/users/me 带/无 token / 错误格式 token
- /api/users 公开列表
- 普通用户 token 不能创建文章
- 管理员密码仍能 CRUD 文章
- /api/users/logout 撤销 token，撤销后同 token 失效
- 9 个静态资源 / 渲染检查 / 白名单回归（含新增 login.html register.html）

### 教训
- **认证设计不要引第三方**：Node 内置 `crypto.scrypt` 就够用，避免装 bcrypt（编译依赖、原生模块），兼容各种部署环境
- **前后端 token 同步**：localStorage 在多 tab 间共享，所以一个 tab 登录，其他 tab 刷新就能拿到 token — 不用做 broadcastChannel
- **白名单要常更新**：新增页面（login/register）必须同步更新 `STATIC_WHITELIST_HTML`，否则 404 — 已加到 v2.7 教训里的 checklist

## v2.8.1：登录注册 nav 右侧化 + fetch 错误诊断

### 用户反馈 v5
1. "登陆注册单独 放在右边" — 之前登录注册跟主导航挤在一排，现在改成独立 group 在右
2. "网络错误" — 注册时 fetch 显示 "Failed to fetch"，用户不知道为什么

### 改动
**A. nav flex 化（左侧主导航 + 右侧登录注册）**
- `.topnav-row` 用 `display: flex; justify-content: space-between`
- `.topnav-left` 装主导航 form 们（搜索/关于/标签/写作/首页）

- 这样右上角红框位置就只显示登录/注册（或用户名），与主导航分组清楚

**B. fetch 错误诊断**
- 登录/注册 catch 块：`window.location.protocol === 'file:'` 检测 → 提示"请通过 http://localhost:8080/ 访问"
- 否则 → 提示"请确认后端服务器正在运行：node server.js"
- `res.json().catch(() => ({}))` 避免服务端返回非 JSON 也崩

### "Failed to fetch" 最常见原因（猜测）
- **用户在 IDE 内部预览工具打开 register.html** → URL 是 file://，浏览器拒绝跨协议 fetch localhost
- 验证：让用户打开浏览器开发者工具 Network 选项卡看请求 URL；如果是 file:// 协议就改用 http://localhost:8080/register.html 访问
- 也可能：用户的浏览器缓存了旧版本 app.js → 强刷 Ctrl+F5

### 教训
- **fetch 错误要给诊断提示而不是泛泛"网络错误"**：TypeError: Failed to fetch 这个异常的根因太多（offline / CORS / file:// / 服务挂 / DNS），光看 e.message 没法定位，必须根据上下文（window.location.protocol、navigator.onLine 等）给出针对性提示
- **flex 分栏是 nav 独立分组的最简写法**：用 `display: flex; justify-content: space-between` 一行 CSS 就做出"左主导航 + 右用户区"的 LWN 风，不需要 grid 或 float

## v2.8.2：CSS specificity 坑（登录注册放右边不生效）

### 问题
`.topnav-row { display: flex }` 看似对，但页面里 `<div class="not-handset topnav-row">` 同时匹配这两个选择器
- 已有 `.not-handset { display: inline-block; }` 在 `@media screen and (min-width: 48em)` 块里
- 新加的 `.topnav-row { display: flex }` 在全局

两者 specificity 都是 (0,1,0)，CSS 按位置**后定义者胜出** —— 那条 `.not-handset { display: inline-block }` 在媒体块内，它胜出 → flex 不生效 → 登录注册掉到左下角

### 修复
用 `.not-handset.topnav-row` 双 class 选择器，specificity 升到 (0,2,0)，永远赢过单独 `.not-handset`：
```css
.not-handset.topnav-row {
  display: flex;
  ...
}
```

### 教训
- **CSS specificity 等同时，定义顺序就是规则**：.X { } 跟 .X { } 一致时最后写的赢。这是隐性 bug，必须按 specificity 比较后才能定位
- **加新样式先 grep 现有的同名 class**："我加 .topnav-row 就行"是不够的——还需要看现有 `.not-handset`、`.rightcol` 等是否设了 display 并同 specificity

## v2.9.1：hljs CDN 选错 + TOC 多级

### 用户反馈 v7
1. "做全一点 2 级 3 级也要有" — TOC 只显示 H2，要把 H3/H4 一起加进
2. "还是没有高亮" — 代码块仍灰底无语法高亮

- 同时删除之前试图单文件加载各种语言的 17 个 `<script>` 行 —— 它们都多余，反而会报重复注册

**B. TOC 多级**
- `querySelectorAll('h2, h3')` 扩展到 `querySelectorAll('h2, h3, h4')`
- 每个标题按 tagName 取 class：`article-toc-h2` (主级) / `article-toc-h3` (中缩进) / `article-toc-h4` (深缩进)
- CSS 对应：H2 不缩进粗体；H3 缩进 0.7em；H4 缩进 1.4em + 灰色（var(--VLinkColor)）+ 字号 0.9em

### 测试
- TOC 13/13 PASS（H2/H3/H4 都进、计数对、过滤评论）
- cdnjs highlight.min.js HTTP 200，121KB

### 教训
- **jsdelivr 上 `lib/*` 路径是 Node 模块结构（require）**，cdnjs 的 `highlight.min.js` 才是浏览器打包版。挑选 CDN 包时一定要看文件头几行，看是不是 `var hljs=...` 还是 `var hljs=require(...)`
- **cdnjs 的 hljs 内置 35+ 语言** —— 不要再额外加载单语言文件（除了非主流语言如 sol/routeros 等）
- **TOC 应当到所有级别**：现代技术博客常有多级标题（H2 章节 / H3 子章节 / H4 详细点），用户期望完整看到，不是只看一级
